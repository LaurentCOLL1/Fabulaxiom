## 2. Chosen P1 topology, without production activation

**Chosen first topology:** a single Fabulaxiom-owned Rust *session actor* owns the one qualifying SQLite connection, VFS registration lifetime, delegated main file, applicable sidecar/mapping lifecycle, transaction sequencing and future admission state. The writer service can be invoked only inside this actor once a future, separately qualified admission token exists. Cooperating same-SID peer processes do not open a second writer; a named mutex may coordinate process ownership, but a mutex is neither file security nor provenance.

**Model and UI isolation:** Tauri/UI requests and future Ollama integration receive typed, bounded requests/results, not sqlite3_file, raw DB paths or the admission token. Future M4 narrative retrieval first uses the **same owner actor** for brief database reads and then returns an immutable, cited packet in memory. No second read-only SQLite connection is introduced in phase P1-0. P1-0 avoids making M4 dependent on a second WAL/SHM open; it does **not** resolve the existing P1 main-file and sidecar proof obligations.

**Alternatives deferred:** (a) extra SQLite readers, even SQLITE_OPEN_READONLY, require separate snapshot, WAL/-shm, namespace and busy/recovery tests; read-only mode does not imply side-effect-free opening. (b) a materialized immutable read database/snapshot requires its own authenticated creation, backup and deletion policy. (c) P2 broker/isolated principal requires a new security and IPC gate. Never turn on PRAGMA locking_mode=EXCLUSIVE as a shortcut: WAL's no-shared-memory variant has lifecycle and interoperability consequences and needs its own review. No unreviewed change in journal_mode or locking_mode is authorized.

## 3. Ownership state machine and refusal semantics

| State | Required evidence / allowed operation | Explicitly forbidden transition |
|---|---|---|
| **A0_STOP** (today) | Cross-process EXISTING_PROFILE remains refused; NEW_ONLY only under existing disposable CI scope | Existing operator profile → admitted |
| **NO_SESSION** (future design) | An authorized owner profile/SID, instance identity, intended VFS and no unexplained predecessor | Assumed clean solely because no mutex/sidecar name is observed |
| **CLAIM_PROVISIONAL** | Named mutex namespace, owner/SID, DACL, process/session identity, bounded wait and cooperative claim checked; no SQLite SQL or writer token | WAIT_ABANDONED / timeout / mismatched owner → admitted |
| **OPENED_UNVERIFIED** | Delegated xOpen may already have caused OS open effects; verify the *actual* returned handle's volume + FileId128 and pinned directory lineage before success, with xClose on veto | Pre-open path identity → claim of atomic open; mismatch → success |
| **SIDECARS_UNVERIFIED** | Account for journal and -wal opens and the -shm mapping path through xShmMap/xShmLock/xShmUnmap; method-version and cleanup behavior | Main-file xOpen pass → all sidecars trusted |
| **IDENTITY_BOUND_UNADMITTED** | Exact profile, schema/foreign keys/migration lineage and journal/recovery state examined only through an independently reviewed safe sequence (SQLite may perform IO during open) | Running SQL presumed side-effect-free before evidence |
| **SESSION_ADMITTED** (hypothetical) | All R1–R9 verified, independent safety review and **separate owner runtime authorization**; private generation-bound admission token | This document/test CI → production V7WriterAdmission |
| **QUIESCING / CLOSED_ATTESTED** | Stop new requests, settle transaction/checkpoint per reviewed policy, close each SQLite/VFS resource, record independently checkable durable provenance | Drop/mutex release alone → clean historical attestation |
| **RECOVERY_REQUIRED_NOT_AUTHORIZED / REVOKED** | Any ambiguous main/sidecar identity, crash, WAIT_ABANDONED, lost worker, stale generation, failed xClose, inconsistent provenance or disputed sequence → fail closed | Automatic repair, recovery, migration or EXISTING_PROFILE reopen |

There must be **one live generation** for the selected profile. Admission tokens and read packets are bound to a session generation; a later process cannot reuse them. Failures revoke the generation and refuse subsequent queued writes. Define the precise creation/cleanup/restart order **before** writing source. A predelegation check is not an atomic kernel identity claim; the last comparison is against the real delegated handle. Some filesystem effects can precede a veto and must be audited.

## 5. SQL, snapshots, WAL and Ollama read consistency

**Proposed P1-0 read algorithm (no executable code):**

1. Validate a typed request: selected universe/novel/scene, point of view, event date, narration ordering, character knowledge, reader reveal limit, requested model role, permitted source classes and maximum evidence budget. Reject cross-universe references and a stale application/session generation.
2. The **same Rust owner actor** serializes a short read of canon, source fiches and relevant historical revisions using its one qualified SQLite connection. A future implementation may need an explicit read transaction/snapshot and invariant testing; do not infer a consistent multi-query snapshot merely from queued commands. **Finish and release** the read phase *before* any long-running Ollama inference/streaming.
3. Build an immutable NarrativeContextPacket with source entity/revision IDs, provenance, revision/hash, valid-time and narration/reveal ordering, canon/draft/unknown/conflict labels and citations. Version it against source change state, not just embedding-cache version. Derived FTS5/embeddings/summaries are rebuildable, never authority.
4. Supply only the bounded packet to the locally configured Ollama chat model. Treat generated text and extracted facts as **untrusted proposals** even under the trusted same-SID OS-process assumption: a language model can hallucinate or follow hostile text inside a fiche. No filesystem, SQL, write-capable tools or automatic cloud endpoint fallback.
5. If canon/history changes while generation is running, mark the packet stale and require revalidation before showing an actionable fact/canon proposal. M6 deterministic contradictions and spoiler/knowledge checks first; user must explicitly review and perform APPROVE_CANON for canon, with separate authorized persistence. Cancellation/timeouts discard or mark outputs, never leave a transaction or lock held across inference.

**Important WAL limit:** official SQLite documentation states that WAL readers may need existing or creatable -wal/-shm files, while a custom VFS's xShmMap path is distinct from xOpen. This forbids claiming that a separate SQLITE_OPEN_READONLY connection is automatically passive or provenance-qualified. The first P1 design deliberately has no second reader. Source references: [SQLite VFS](https://www.sqlite.org/c3ref/vfs.html), [io_methods](https://www.sqlite.org/c3ref/io_methods.html), [WAL, read-only and shared memory](https://www.sqlite.org/wal.html), [SQLite result codes](https://www.sqlite.org/rescode.html), [Win32 CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), [Win32 named mutex](https://learn.microsoft.com/en-us/windows/win32/sync/mutex-objects).
