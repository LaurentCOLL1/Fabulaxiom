## New source and schema

`tools/m3_2_provenance_triage.py` accepts only `--claims-json <path> --dry-run` and is **not part of application startup**. Its JSON input must be an array containing exactly five objects with these keys: `root`, `role`, `observed_sha256`, `evidence_kind`, `evidence_uri`, `recorded_at`, `custodian`, `record_id`. Observed digests must equal the three checked-in *recent* digests; unanchored roles must use `null`, never a freshly generated SHA. Evidence kind is `none`, `recent_observation`, or `prior_external_claim`. The prior claim type requires a proper HTTPS URL without credentials, ISO-8601 offset-aware claimed date/time, nonempty custodian and record identifier, but neither the URL nor contents nor signature is fetched or trusted by the checker.

The validator **never promotes** any of the five roles to historically attested, even if all five claim prior external records. It returns a pending-only JSON summary with `independently_verified_historical_claims=0`, `historical_promotions=0`, `m32_staging_authorized=false`, `operator_live_qualified=false`, and flags that it did not open SQLite/protected files, write, fetch URLs or verify signatures. Malformed/unmatched/duplicate metadata returns FAIL. Both outcomes have CLI exit **2**; a successful triage is NOT an approval. The program doesn't output original URLs, custodians, or evidence metadata, avoiding disclosure through CI logs.

## 2026-10-14 — Stage 19.1: untrusted JSON intake hardening (NEW SHA qualification required)

**Accepted predecessor:** Stage 19 exact source `3c237179396bafafd5c4733a5f6f3ae7a7355ac7`, Windows pull_request CI #38503049446 **completed/success 31/31**. **Weakness:** the Stage-19 CLI checked file type via `is_file()`, size via `stat()`, then called `read_text()` once and used the default JSON parser. This permitted indirect traversal through existing symlinks/junctions/reparse points and allowed JSON objects with duplicate keys to silently overwrite earlier values. Separate size-check and read calls also left ordinary between-read content changes unchecked.

**Stage 19.1 source-only correction:** `read_claims_readonly(path)` requires an **absolute path**, rejects explicitly named protected production/M2.5/M3.1/ACL directories and source worktrees, invokes pre/post `regular_safe` checks on the file and existing ancestors, requires regular file with size **1..16384 bytes**, and compares file metadata (device, inode, mode, length, mtime_ns, ctime_ns) before/after. It reads via bounded 16385-byte reader **twice**, compares the bytes, and checks metadata before parsing. On platforms with `O_NOFOLLOW`, use it in `os.open`; Windows lacks an equivalent in this wrapper so pre/post reparse checks are best-effort—not an atomic or adversarial-race-proof filesystem snapshot. Nothing may be deleted or modified on detected ambiguity. UTF-8 decode must succeed; `json.loads(object_pairs_hook=...)` rejects **any duplicate key, including nested objects**, and `parse_constant` rejects nonstandard `NaN`/`Infinity`. Semantic 5-role truth (21 historically pinned, 3 observational, 2 unanchored) and no-promotion behavior is unchanged.
