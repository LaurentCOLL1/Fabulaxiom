## Code préparé et invariants

- `src-tauri/src/m32_v7_writer_service.rs` **compilé dans le backend**, mais **sans référence depuis les commandes Tauri, sans état enregistré, sans nouveau point d'entrée IPC ni ouverture par chemin**. Le constructeur prend une **connexion déjà ouverte et admise** ; il exige un type `V7WriterAdmission` dont le champ privé n'a **aucun constructeur hors test**. Aucun usage opérateur ne peut donc être instancié sans une future modification et revue explicites de la source.
- La connexion unique est déplacée dans un worker Rust ; les clients ne reçoivent que des clones d'un `SyncSender<Command>` **borné à 8**. Commandes typées existantes seulement : créer une révision de scène, choisir la révision courante, modifier la visibilité d'une révision, lire l'historique. Aucune SQL brute transmise par la WebView.
- La connexion est configurée en `TransactionBehavior::Immediate` **avant** les commandes : les fonctions de révision existantes qui appellent `Connection::transaction()` utilisent ainsi `BEGIN IMMEDIATE`. SQLite peut répondre `SQLITE_BUSY` en cas de conflit externe ; le service limite le `busy_timeout` à trois secondes, ne fait aucun repli en réouverture et conserve l'erreur applicative. Une file interne ne bloque **pas** une autre connexion OS : la sérialisation inter-processus reste la responsabilité des verrous SQLite.
- L'admission locale (en plus du jeton non forgeable) refuse transaction déjà active, `main` read-only, `query_only`, clés étrangères désactivées, version de schéma différente de la version actuellement autorisée, ou `ATTACH` de schéma étranger. Ces tests **ne sont pas** une preuve d'identité de chemin/handle, de journaux ou de chaîne de conservation.
- Le client utilise `try_send`: en saturation, `QueueFull` (refus sans attendre) ; après fermeture, `Disconnected`. L'arrêt explicite envoie `Stop`, joint le worker et fait tomber **la même** connexion. Aucune migration, backup, checkpoint, connexion de secours, second profil ou nouvelle base n'est créé par le service.

## Tests sur données inventées, jamais sur l'opérateur

Huit nouveaux tests Rust `#[cfg(test)]` utilisent exclusivement `Connection::open_in_memory()` et une hiérarchie de scène fictive initialisée **uniquement dans les fixtures** par les migrations existantes autorisées. ## Ce que la préparation NE résout PAS

Le service n'est **pas activé** ; il n'existe aucun émetteur de jeton d'admission en runtime, aucune preuve de l'identité atomique du handle SQLite, aucune exclusivité garantie contre un processus hostile extérieur, aucune qualification des sidecars `-wal`, `-shm`, `-journal` en exploitation, ni migration réelle ou changement de `database::open_database` pour les commandes actuelles. Avant un chemin applicatif effectif : une **nouvelle autorisation distincte** doit décrire l'admission v7 du même profil, la politique de menace/processus, les refus, l'observabilité, le modèle de crash/stop, les fichiers accessoires et les données Windows privées. Ne pas inférer que `single-instance`, `query_only`, `FILE_SHARE_WRITE` ou un FileId ponctuel établissent une exclusion globale des écrivains.
